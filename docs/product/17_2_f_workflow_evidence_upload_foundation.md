# PR17.2F Workflow Evidence Upload Foundation

> **Status:** PR17.2 planned implementation split.
> **Decision:** PR17.2F is split into F1 and F2 so the storage/RLS/RPC trust boundary lands before browser form work.

PR17.2E proves the leave and expense workflow notification loop at the database boundary. PR17.2F opens the next product edge: evidence files for leave requests, expense receipts, and contract documents. This is not OCR, AI extraction, e-signature, external delivery, or automatic canonical writeback.

## Why a staging table is required

The existing domain metadata tables cannot accept pre-uploaded files:

- `puls_workflow.leave_documents.leave_request_id` is `NOT NULL`.
- `puls_workflow.expense_receipts.expense_claim_id` is `NOT NULL`.
- `puls_workflow.contract_files.contract_id` is `NOT NULL`.

At the same time, current workflow RPCs reject required-document and required-receipt cases before the parent request/claim can be created. Making the existing foreign keys nullable would spread upload lifecycle state across three domain tables and widen three RLS surfaces. PR17.2F therefore uses one staging table, `puls_workflow.evidence_uploads`, and attaches finalized evidence to the domain tables only after the parent object exists.

## PR17.2F1 Backend Boundary

F1 creates the evidence trust boundary without changing visible forms:

1. Private storage bucket for workflow evidence.
2. `puls_workflow.evidence_uploads` staging table with tenant, owner, domain, storage path, declared file metadata, status, expiry, and scan posture.
3. Browser-safe RPCs to create and finalize upload intents.
4. Storage object RLS tied to existing upload intents; no public URLs.
5. Direct browser insert/update into `leave_documents`, `expense_receipts`, and `contract_files` is closed; future writes go through RPCs.
6. Existing domain metadata SELECT policies are extended so assigned approvers can read attached leave/expense evidence metadata.
7. `contract_files` gains uploader metadata and keeps `metadata_only` as "database row stores metadata only; binary lives in private storage".
8. Contract evidence can be attached through an admin-only RPC because the contract parent already exists.
9. Safe audit rows are written for intent creation, finalize, and contract attach.

F1 must not add OCR, file parsing, virus-scan claims, browser UI, leave/expense submit-with-evidence, notification summary enrichment, signed URL UI, or AI context feeding.

## PR17.2F2 Product Flow

F2 binds the foundation to product workflows:

1. Leave form shows a compact evidence upload field only when the selected leave type requires a document, or when optional evidence is allowed.
2. Expense form shows receipt upload when the selected category and amount require it.
3. New submit RPCs attach finalized evidence atomically:
   - `create_leave_request_with_evidence(...)`
   - `create_expense_claim_with_evidence(...)`
4. Existing no-evidence RPCs remain valid for ordinary leave and expense flows.
5. Contract UI opens admin upload and authorized viewing against the F1 contract evidence RPC.
6. Browser form states stay compact: file chip, upload status, remove-before-submit, one primary CTA.
7. Notification dispatch dedupe keys and PR17.2E smoke invariants remain unchanged.

## Security and Honesty Rules

- File binary is stored only in the private workflow evidence bucket.
- Storage paths are generated by the server; raw filenames are display metadata only.
- Public URLs are forbidden.
- `sha256_client` is client-declared integrity metadata. It is not presented as server-verified content hash.
- MIME and size validation in F1 uses declared metadata, extension allowlist, storage object existence, and conservative byte limits. Deep content sniffing, malware scanning, and OCR are separate services and are not claimed here.
- `scan_status = 'not_scanned'` is honest default posture. Downloads can be permission-gated without claiming antivirus coverage.
- Orphan uploads expire. `expired` staging rows cannot be attached.
- Approvers can read only attached domain evidence for requests they are assigned to approve. They never see unattached staging uploads.
- Audit metadata must not include raw file contents, document text, receipt OCR values, credential values, provider payloads, or decision notes.

## Accepted File Policy for F1

| Domain | MIME types | Max size | Notes |
| --- | --- | --- | --- |
| Leave | `application/pdf`, `image/png`, `image/jpeg` | 10 MB | Evidence only; no OCR. |
| Expense | `application/pdf`, `image/png`, `image/jpeg` | 10 MB | Receipt OCR deferred to PR17.2G. |
| Contract | `application/pdf` | 15 MB | PDF only in F1; DOCX/e-signature remains future scope. |

## Acceptance Criteria

F1 is complete when:

- A workflow evidence bucket exists and is private.
- `evidence_uploads` is tenant-bound, RLS-protected, and has server-generated storage paths.
- Authenticated users can create upload intents only for their tenant and allowed domains.
- Finalize succeeds only for owned, unexpired intents with allowed domain/mime/size and an existing storage object.
- Direct authenticated inserts/updates into domain metadata tables are blocked.
- Attached leave/expense evidence metadata is visible to owner, admin, manager, and assigned approver.
- Contract file evidence can be attached by admins without exposing raw file data.
- Audit rows are metadata-only.
- `pnpm run verify:pr17` includes the PR17.2F1 verifier.

F2 is complete when:

- Required-document leave requests can be submitted with evidence and are rejected without evidence.
- Receipt-required expenses can be submitted with evidence and are rejected without evidence.
- The leave, expense, and contract UI no longer shows dead disabled upload controls.
- Browser UI remains compact and does not display release notes or development explanations.
- PR17.2E notification/reconcile invariants still pass.

## Non-Goals

- OCR, AI extraction, vendor/date/amount parsing.
- Human review of OCR confidence.
- Antivirus or server-verified file hash claims.
- E-mail, mobile push, external file sharing, or e-signature.
- Canonical HR mutation based on file contents.
- Notification safe-summary enrichment for evidence counts.
